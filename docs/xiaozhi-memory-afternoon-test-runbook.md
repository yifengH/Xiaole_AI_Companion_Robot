# Xiaozhi AI 记忆 A/B 对比测试：单下午逐步操作手册

> 版本：v1.0  
> 预计用时：约 4 小时 45 分钟（示例：13:00～17:45）  
> 执行方式：一名测试者、两台服务器并排操作、单次探索性对比  
> 关联文档：[完整测试设计与全部题库](xiaozhi-memory-ab-test-plan.md)

## 先看结论：今天下午你要完成什么

今天只完成一轮“即时、跨新会话”的快速对比，不做 24 小时或 7 天保持测试。你将依次完成：

1. 每台服务器准备三个相互隔离的身份：一次性空白检查、正式实验、跨账号隔离。
2. 确认两台服务器当前没有旧记忆。
3. 给两台服务器逐字投喂完全相同的 4 段人物背景对话，共 50 个用户轮次。
4. 每段投喂结束后退出当前对话，等待 5 分钟，再开启新对话。
5. 再进行 12 轮无关聊天，结束对话并强制等待 15 分钟。
6. 在新对话中执行 26 道精选测试题；原则上每道题都重新开启一个新对话。
7. 最后执行跨账号隔离和全量清除测试。
8. 按 0～4 分打分，计算两边总分、分维度得分和胜/平/负。

今天的结果适合回答：“两套系统在一次下午的真实聊天后，谁的即时跨会话记忆体验更好？”它不能证明谁的 7 天或 30 天长期记忆更好，也不能以单次运行代表稳定平均水平。

## 0. 今天需要准备的东西

### 0.1 账号和设备

为每台服务器准备三个账号或相互隔离的用户/设备 ID：

| 用途 | 自建服务器 A | Xiaozhi 服务器 B |
| --- | --- | --- |
| 一次性空白检查账号 | `A-check` | `B-check` |
| 正式实验账号 | `A-run1` | `B-run1` |
| 隔离测试账号 | `A-isolation` | `B-isolation` |

如果系统没有“账号”概念，请使用不同的设备 ID、用户 ID、角色 ID、Agent ID 或记忆命名空间。关键要求是：`check`、`run1` 和 `isolation` 之间不能共享任何记忆。若确实只能建立两个账号，隔离测试前必须再次彻底清空 `check`，并尽可能通过后台确认其记忆条目为 0。

### 0.2 建议的输入方式

第一轮优先使用文本输入，因为这样最容易保证两端收到完全相同的内容。若必须使用语音：

- 两台设备不要同时外放，避免 A 的回答被 B 当成用户输入。
- 操作 A 时将 B 静音或移开；操作 B 时反过来。
- 每句话用正常但清晰的语速说一遍，不额外发挥。
- 能看到 ASR 转写时，务必保存转写文本。
- 若一端把关键事实听错，两端都重新说一遍同一句，并在记录里写 `FEED-RETRY`；不要只给听错的一端重复，否则两边的强化次数不同。

### 0.3 打开四个窗口

开始前建议打开：

1. 服务器 A 的对话窗口或设备控制界面。
2. 服务器 B 的对话窗口或设备控制界面。
3. 本操作手册。
4. 一个记录文件、电子表格或纸质记录表。

建议把 A 固定放在左边、B 固定放在右边。测试完成并打完分之前，不交换位置，避免抄错回答。

### 0.4 必须记录的基本信息

开始前填好：

| 项目 | 服务器 A | 服务器 B |
| --- | --- | --- |
| 服务器名称/地址（可用简称） |  |  |
| 测试账号或设备 ID |  |  |
| 模型名称/版本；不知道写 `unknown` |  |  |
| 记忆功能是否开启 |  |  |
| 角色/系统提示词是否一致 |  |  |
| 输入方式：文本/语音 |  |  |
| 开始时间 |  |  |
| 时区 | Asia/Shanghai | Asia/Shanghai |

### 0.5 今天的三条硬规则

1. **两端只说相同的话。**不要因为某一端追问得更好，就多告诉它信息。
2. **不纠正测试答案。**正式测试阶段，无论系统答得对不对，都只记录，不说“对”“不对”或正确答案。
3. **测试题之间切换新对话。**这样尽量避免上一题的回答成为下一题的新记忆。

## 4. 投喂时的统一操作方式

每一个编号都按下面的固定节奏操作：

1. 对本会话的“先手服务器”说出该句，等待完整回答。
2. 立刻记录该端回答是否明显听错或理解错；不评分，也不纠正。
3. 对另一台服务器说完全相同的一句，等待完整回答。
4. 记录异常，然后进入下一句。

为减少总是 A 先听到的顺序偏差：

- 会话 1：A 先、B 后。
- 会话 2：B 先、A 后。
- 会话 3：A 先、B 后。
- 会话 4：B 先、A 后。
- 干扰对话：A 先、B 后。
- 正式测试：奇数题 A 先，偶数题 B 先。

### 系统追问时怎么处理

如果系统问“你为什么喜欢摄影”“年糕多大”等问题，不回答它的追问，直接说脚本中的下一句。不要说“这个以后再说”，因为这也会成为额外输入。

### 系统理解错时怎么处理

- 轻微理解错：只记录，不纠正。
- ASR 把关键事实转写错，例如把“陈琦”写成“陈琪”：两端都把原句完整重复一次，并标记 `FEED-RETRY`。
- 网络超时：同一句对两端都重发一次，标记 `NET-RETRY`。
- 一端连续两次失败：暂停计时，修复后从该句重新对两端发送；不要让一边少听或多听。

## 10. 第八步：正式测试前的记录规则（16:05）

### 10.1 每道题的会话规则

最佳执行方式是每一道题都这样做：

1. A、B 都新建空白会话。
2. 奇数题先问 A，偶数题先问 B。
3. 问完一端后立即保存完整原文，再问另一端。
4. 两端都回答完后，结束两边当前对话。
5. 等待约 5～10 秒，确认会话已结束，再进行下一题。

不要在同一会话里连续问 26 题。上一题的提问和系统回答可能写回记忆，污染后面的题。

新建会话只能切断短上下文，未必能阻止系统把测试题或自身回答写入长期记忆。本下午版没有记忆快照，因此题目顺序已经刻意安排为“自然关联/应用在前，直接事实与反诱导在后”，并尽量避免后题依赖前题答案；这仍是快速实验的已知限制。

如果你的客户端无法做到每题新建会话，可以每 4 题新建一次，但必须在结果报告中注明：“测试题按四题一组，存在题间记忆污染风险。”

### 10.2 系统反问时的统一处理

如果系统只反问、不作答，例如“你指的是哪件事？”，对两端都补充同一句：

`请根据你已经知道的信息直接回答；如果不确定，就明确说不确定。`

补充后得到的答案最高只能评 3 分，因为已经需要额外提示。记录 `CLARIFY`。

### 10.3 正式测试阶段禁止说的话

不要说：

- `对，就是这样。`
- `不对，是下周三。`
- `你记得真好。`
- `另一台服务器答得比你好。`
- `我再给你提示一下。`

这些内容会改变后续记忆或引入评分偏差。

## 11. 第九步：26 道正式测试题（16:05～17:10）

### 11.1 评分方法

每题分别给 A、B 打 0～4 分：

| 分数 | 现场判定 |
| --- | --- |
| 4 | 关键点全部正确，使用最新信息，无编造，回答与问题自然相关 |
| 3 | 核心正确，只有轻微遗漏或表达问题 |
| 2 | 部分正确，但漏掉重要点或帮助有限 |

## 16. 中途出现问题时怎么处理

| 问题 | 现场处理 |
| --- | --- |
| 一端断网/超时 | 暂停两端；修复后同一句对两端都重发；记录 `NET-RETRY` |
| 一端关键 ASR 转写错误 | 同一句对两端都重新说一遍；记录 `FEED-RETRY` 或 `TEST-RETRY` |
| 忘了退出会话 | 立即退出并记录；若已开始下一阶段，将该阶段标记“可能受短上下文污染” |
| 等待时间少于要求 | 补足剩余时间后再继续；不要从发现问题的时刻重新投喂 |
| 脚本说错了一句 | 不即兴改写；对两端统一说：`我纠正一下，刚才那句应当是：……`，记录纠错 |
| 只对一端多说了一句话 | 将完全相同的话补给另一端并记录；若无法补齐，本轮公平性受损 |
| 系统问了很多追问 | 不回答，直接进入下一条固定脚本 |
| 正式题不回答只反问 | 使用统一澄清句；最高 3 分并标记 `CLARIFY` |
| 误说出了正确答案 | 该题作废，不计分；不要再换个说法重测同一账号 |
| 发现正式账号有旧记忆 | 本轮作废，重新建立正式账号；不能继续“将就测试” |
